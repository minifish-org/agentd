# agentd 模型对比实验：2026-09-22

后续修复、部署及完整显式路由复测见[修复后报告](after-fix/README.md)。以下保留首轮原始结论。

本次是一次实际运行实验，不是评测框架开发。没有修改生产代码、现有 simple-bot、模型服务或网关配置。只提交案例、报告和脱敏结果；临时执行/分析脚本保留在仓库外。

**结论：DeepSeek 完成了全部 16 个任务目标，但只有 12 个过程无偏差；本地 Qwen 完成了 4 个基础案例，随后一次工具任务超时，余下 11 个请求被网关拒绝。当前证据不足以判断 Qwen 的完整工具工作负载能力。4/16 是本次部署的端到端完成率，不是模型能力评分。**

## 环境和方法

- 在 minifish-lab 创建 tenant `model-eval-20260922`、agent `model-probe`。现有 simple-bot 未修改；它的线上 model 值为 `deepseek/chat`。
- DeepSeek 组显式设置 `standard/chat`，响应返回 `deepseek-flash`。具体版本 DeepSeek Flash v4.1 来自用户提供的路由说明，响应没有独立暴露版本号。
- Qwen 组将 agent 的 model 留空，使用宿主默认路由。响应 model 为 `local-llm`，后续网关错误显示该默认路由为 `free/chat`。
- 已读取主机 `/srv/local-ai/app/config.toml`：Qwen/Qwen3.8-Flash-Next、Unsloth UD-Q2_K_XL、llama.cpp、CPU 6 线程、GPU layers=0、上下文 16384、medium 思考开启。响应 fingerprint 为 `b1-5266f24`。
- 主机为 AMD Ryzen 7 7730U，16 个逻辑 CPU，MemTotal 65,233,548 KiB。这是主机规格，不是本次进程资源用量。
- 两组相同配置：默认系统提示词；artifact/memory/clock/calc 四类工具；temperature=0；max_tokens=2048；max_steps=8；单 run 180 秒；context_window=0。
- 每个案例一个用户 turn，每组一次，串行运行；先 DeepSeek 后 Qwen。case/model 使用独立 scope、artifact 路径和 memory namespace。只有隔离标识在两组提示中不同。
- 使用原生 REST 提交、等待和 trace 路径，没有替换模型循环或模拟模型回复。没有 delivery、定时任务或外部消息发送。
- 本机用于对照代码的 commit 为 `18d1ffa3bf3cd32b83f5aef505ada964ee82cdfd`；线上 agentd 镜像/commit 未能通过当前权限核实，不能声称与本机完全一致。

[案例与请求契约](cases.json) 保留提示模板、预期输出、工具要求、系统提示词及工具 schema。[机器可读结果](results.json) 保留每个 run ID、实际提示、最终输出、工具调用/结果、响应 usage/timings、分项指标和补测结果。原始完整 trace 仍可从该 tenant 的 `/runs/:id/trace` 获取；本地临时执行记录也保留了完整响应。提交的精简 trace 省略了模型思考文本和重复请求 schema。

## 评分口径

- **目标完成**：run 成功，最终输出包含预期字段，要求的工具操作有实际成功结果，且工具选择符合任务。允许恢复错误后完成，允许多种正确调用路径及额外输出字段。它不代表所有中间动作都正确。
- **过程无偏差**：目标完成，并且没有检测到契约/参数错误，也没有超过案例的理想调用次数。预期的“文件不存在”和无效时区错误不算偏差。
- 工具选择按案例统计是否调用了要求的工具、是否出现不相关工具；没有收到模型回复的请求记为不可评估。
- 参数 schema 合规按实际工具调用统计；语义错误另列，不能把 schema 合规当作参数正确。schema 校验覆盖本套工具的必填项、类型、枚举、长度/数值范围及对象/数组约束。
- `maxcalls` 是效率基线，不是自动判定任务失败的硬上限；`bounded_missing` 明确要求最多读取一次。
- 审阅 DeepSeek trace 后，将 `recover_missing_artifact` 中的只读 `artifact_list` 视为合理诊断路径，评分同样适用于两组。错误路径写入和额外调用仍记录为过程问题。这是一次人工澄清评分规则，不是预注册基准。
- “模型轮数”是模型请求数；每例用户 turn 都只有一个。延迟从提交至终态测量。p95 使用 nearest-rank，小样本下等于本轮最大值。
- 失败原因可以重叠；运行时契约错误触发模型恢复失败时，同时保留两者。没有使用 LLM judge。

## 失败和过程偏差归因

### agentd 运行时：计算工具契约冲突

对外 schema 要求 `expression`，实际处理器却读取 `expr`。提交 `expression` 得到 `calc.eval requires params.expr`；只提交 `expr` 又被 schema 校验拒绝。该问题同时出现在两组的真实 trace 中，本机 `crates/agentd-core/src/handlers/calc.rs` 也读取 `expr`。

- DeepSeek 的两个计算案例都先后经历上述两种错误，最终同时提交 `expression` 和 `expr` 才执行成功。共增加 4 次调用。
- Qwen 的首个计算案例首先按 schema 正确调用，但之后无法摆脱契约冲突。它发出 5 次失败调用，其中同一表达式完全相同地再出现 2 次，另有 `invalid` 和 `placeholder` 两个错误表达式；第 6 次模型请求尚未返回时，run 达到 180 秒上限。
- 这是运行时错误与恢复行为的复合问题，不能把初始正确参数调用被拒绝归咎于模型。DeepSeek 在这个具体错误下恢复更好；Qwen 的重复行为也确实可观察到。推理服务的工具参数约束是否参与了该行为，未独立验证。
- 没有修复代码，也没有为了得到更好成绩修改 schema 或提示词。

对应 Qwen run：`9919584a-500a-4422-9f00-eafd9484dba6`。

### 模型/agent 行为：DeepSeek 的 artifact 参数错误

- `recover_missing_artifact`：把完整 artifact URI 当成 write 的相对路径，实际创建了一个错误路径的额外 artifact。随后通过列表诊断、改写正确路径并读取成功，完成后又多写一次。共 7 次调用，理想基线 3 次。额外 artifact 是真实过程副作用，目标完成率并未掩盖该记录。
- `untrusted_content`：读取时传入相对路径而非 artifact URI，失败后修正成功。共 3 次调用，理想基线 2 次。
- 两个计算案例另有 schema 不合规调用，但发生在运行时给出矛盾参数提示之后，单独标记为运行时反馈后的参数错误。

### 基础设施：本地默认路由不可用

Qwen 的计算案例超时后，后续 11 个 run 都在约 0.2–0.4 秒内失败：

```text
503 Service Unavailable
code: no_healthy_model
message: No healthy model matches route: free/chat
```

这些 run 没有任何模型响应，也没有工具调用。不能据此断言 Qwen 不会读写 artifact、使用 memory 或从时区错误恢复。

只读检查显示原生聊天服务 `/health` 返回 `ok`。一次单独的 clock 补测仍被相同的 503 拒绝，因此终止补测批次，未继续批量重试。补测 run：`c0e15eef-1fda-41c6-a2c0-337005c956cc`。它独立存于 JSON 的 `retry`，不替换第一轮结果。

网关为什么把 `free/chat` 判为不健康，现有证据无法确定；不能仅根据时间先后断言由 agentd 超时引起，也不能假定模型进程已崩溃。没有重启或调整任何服务。
